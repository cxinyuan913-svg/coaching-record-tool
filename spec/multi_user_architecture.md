# 多人使用架構規劃（現階段只規劃，不動程式碼）

## 目的與現況

目前這個工具是單人（教練你自己）在用：沒有登入機制、沒有帳號概念，
全部資料（學生、場地、價目表、套組、課程、額外費用）都是同一份全域
資料，`app/routers/integrations.py` 的 Bearer Token 只是保護「給外部
自動化系統讀資料」這一個端點，不是使用者登入系統。

這份文件先把「以後如果要開放多人使用，要動到哪裡」盤點清楚，**目前
不確定會走哪個方向**，所以先不動現有 schema／程式碼，只整理選項跟
「不管走哪個方向都該先做」的準備工作，供之後決定方向時參考。

---

## 兩種「多人使用」的方向，需要的改動完全不同

### 方向 A：SaaS 多租戶（多個教練各自獨立使用，資料互相看不到）

- 需要新增一張「使用者/教練」帳號表，加上登入機制（session 或 JWT）。
- `students`／`venues`／`price_rules`／`packages` 這幾張「頂層」表要
  加上 `owner_id`（屬於哪個教練），`lessons`／`adjustments` 可以透過
  它們的 `student_id`／`lesson_id` 間接歸屬，不一定要每張表都加欄位，
  但換來的代價是：**幾乎每一支 API 的每一條查詢都要補上「只能查自己
  的資料」這個篩選條件**，漏掉一條就是資料外洩，風險集中在「要逐一
  檢查、不能漏」這件事本身，適合搭配一個共用的 FastAPI 依賴（目前的
  `get_db` 那種模式）強制所有查詢都經過同一個「目前登入者」的過濾器，
  而不是每支路由自己各自記得加。
- 現有真實資料（coaching.db 裡你自己的資料）要一次性遷移，全部指定
  `owner_id` = 你自己的帳號。
- 影響範圍：`app/models.py`（六張表大改）、`app/routers/*.py`（幾乎
  每一支都要改）、需要新增登入頁面／session 中介層。這是這個專案目前
  最大規模的一次改動，等同於重新設計一次。

### 方向 B：共用多人（不隔離資料，例如你自己手機＋電腦同時用，或未來
請助理一起記帳）

- 只需要「登入」（知道現在是誰在操作，方便之後如果要加操作紀錄），
  **不需要**幫每張表加 `owner_id`，因為大家本來就該看到、改到同一份
  資料。改動範圍小很多：一張帳號表 + 登入機制，schema 六張表本身幾乎
  不用動。
- 真正的風險不是「資料要不要隔離」，而是「SQLite 能不能撐得住多人
  同時寫入」。SQLite 開 WAL 模式對「少數幾個人、不算頻繁」的同時寫入
  其實還撐得住，不是絕對不行；但既然都要搬上雲端主機，換成 Postgres
  可以順便拿到更穩的併發寫入、更好的備份工具，是不是一定要現在換，
  可以再議。

### 現在還不確定要走哪個方向 → 兩者都先不要做

因為 A、B 需要的 schema 形狀完全不同（A 要幫表加欄位、B 幾乎不用），
現在硬做其中一種，方向一旦選錯就是白工，甚至要拆掉重做。**建議先做
下面這些「不管選哪條路都用得到」的準備工作就好，schema 本身先不動。**

## 不管走哪個方向都建議先做的準備（低風險、不影響現有功能）

現在程式碼裡有幾個地方寫死綁定 SQLite 語法，如果以後真的要換成
Postgres（不管是方向 A 還是 B），這幾個地方會直接壞掉，建議之後找
時間先處理掉，跟「要不要開放多人」這個決定無關，隨時都可以做：

| 檔案 | 問題 | 為什麼會壞 |
|---|---|---|
| `app/routers/stats.py` 第 144、149、157、160 行 | 用 `func.strftime("%Y-%m", ...)` 依月份分組 | `strftime` 是 SQLite 專屬函式，Postgres 沒有這個函式，換資料庫會直接噴錯 |
| `app/database.py` 第 28~31 行 `_add_column_if_missing` | 用 `PRAGMA table_info(...)` 查表格欄位 | `PRAGMA` 是 SQLite 專屬語法，Postgres 完全不認得 |
| `app/database.py` 第 11~13 行 `create_engine` | `connect_args={"check_same_thread": False}` | 這個參數是 SQLite 的 driver 才認得，Postgres 的 driver（psycopg2）收到這個參數會直接報錯 |

修法方向（先記錄，不現在動）：
- `strftime` 分組改成先把資料撈出來，在 Python 裡用 `date.strftime` 分組
  （量不大，效能差異可忽略），跟資料庫是哪一種完全無關，一勞永逸。
- `PRAGMA table_info` 改用 SQLAlchemy 內建的 `sqlalchemy.inspect(engine)`
  查欄位，這是 SQLAlchemy 提供的跨資料庫 API，SQLite／Postgres 都能用
  同一段程式碼。
- `check_same_thread` 這個參數只在 `DATABASE_URL` 是 `sqlite://` 開頭
  時才加，用 `if SQLALCHEMY_DATABASE_URL.startswith("sqlite")` 判斷。

`DATABASE_URL` 這個環境變數已經是唯一連線設定入口（`app/database.py`
第 8 行），這點已經做對了——之後真的要換資料庫，理論上只要改部署時的
環境變數，不用改程式碼裡到處寫死的連線字串。

## 下一步

等想清楚要走方向 A 還是方向 B，再回來討論：
- 方向 A：需要先設計帳號表欄位、登入方式（session cookie 還是 JWT）、
  以及「目前登入者」怎麼一致地套用到每一支查詢上。
- 方向 B：需要先決定登入機制要多簡單（例如只是共用一組密碼，還是
  每個人各自有帳號但看到同一份資料）。

在那之前，唯一建議做的事就是上面那張表的三個小修正，跟方向無關、
風險低，可以隨時找空檔做掉。
