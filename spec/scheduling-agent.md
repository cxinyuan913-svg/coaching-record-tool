# 找空檔排班 Agent（Phase 2）

## 目的

學生提出時間需求（例如「下週一到五，台北」），系統自動比對既有行事曆，找出最省交通時間的候選時段，產生一段可直接複製給學生的訊息。

## 整體流程

```
學生訊息 → [Phase 1 解析] → 日期時段 + 地區 + 時長 + 學生
        → [Phase 2 找空檔，純程式] → 候選時段
        → [固定範本組字] → 可複製給學生的訊息
```

- 需求解析直接沿用 Phase 1 的 `POST /api/booking-requests/parse` 結果（`resolved_windows`、`area_match`、`student_match`、`duration_minutes`），不再另外呼叫 LLM。
- 訊息文字用固定範本產生，不用 LLM：不花 token、結果可預期、好測試。
- 整個 Phase 2 不呼叫 LLM。

## 新增資料表

```
venue_travel_times (id,
                     venue_a_id FK, venue_b_id FK,
                     travel_minutes)
```

場館兩兩之間的固定車程對照表，同場館車程視為 0，不用建表查詢。

- 雙向共用一筆：存的時候固定 `venue_a_id < venue_b_id`，查詢時兩個方向都查得到。
- 查不到車程的場館組合一律視為「不可銜接」（不要猜一個預設值），跨館候選直接剔除。
- 車程數字由教練提供，不由程式或 AI 推估。

## 架構原則

LLM 只負責理解學生的自然語言（Phase 1 已完成）。實際找空檔的運算邏輯用一般程式處理，不交給 LLM 推理，確保結果可預期、不會算錯。

## 參數與預設值

| 項目 | 規則 |
|---|---|
| 工作時段 | 08:00–22:30。候選不得早於 08:00 開始，也不得晚於 22:30 結束（常數，之後要改只改一個地方） |
| 占用時段的課程 | `status` 為 `scheduled` / `completed`。`cancelled` 與 `leave`（請假）都視為時段已釋放 |
| 候選時長 | 學生訊息有講 → 用訊息的；沒講 → 比對到的學生最近一堂課的 `duration`；都沒有 → 60 分鐘。API 可另外指定覆蓋 |
| 相關場館 | `area_match` 對到的場館；學生沒講地區 → 全部場館。API 可另外指定 `venue_ids` 覆蓋 |
| 學生時段 | 候選的**開始時間**必須落在某一個 `resolved_windows` 內（例如學生說「晚上」，就不會出現下午的候選）。不要求整堂都在裡面：學生說「七點」時換算出的時段是 19:00-20:00，但兩小時的課 19:00-21:00 也符合學生的意思；結束時間由工作時段把關 |
| 貼靠候選上限 | 最多列 5 筆 |

## 候選時段演算法

**貼靠候選**（緊貼既有課程，交通最省）：

1. 撈出學生時段涵蓋日期內的所有占用課程（**所有場館**，因為教練人只有一個，別館的課也會卡住時間）。
2. 對每一筆既有課程（錨點），對每一個相關場館 V，往外長出最多兩個候選時段：
   - 之後：開始時間 = 錨點結束 + 車程(錨點場館 → V)
   - 之前：結束時間 = 錨點開始 − 車程(V → 錨點場館)
   - 同場館車程為 0，就是緊貼。
3. 基本過濾：
   - 超出工作時段 → 剔除
   - 開始時間不在學生時段內 → 剔除
   - 不在相關場館 → 剔除
4. 排除衝突：候選時段前後各加上車程後，跟任何一筆占用課程重疊 → 剔除。也就是說，候選前一堂在別館的話，要來得及趕過來；候選後一堂在別館的話，要來得及趕過去。
5. 跨館門檻：候選跟錨點不同館時，計算候選所在場館當天的連續時數（候選本身，加上同館中跟它首尾相接、間隔 0 分鐘的既有課程），須 ≥ 120 分鐘才通過，否則剔除（去程回程換不到兩小時不划算）。
   - 跟原版的差異：原版把「其他候選」也算進連續時數，但候選之間是互斥的選項，學生最後只會選一個，所以不能加總，這裡只算既有課程。
6. 去重：不同錨點生出的候選，如果日期、時段、場館完全相同，只保留一筆。
7. 排序：同館貼靠優先，再來是跨館貼靠；同一類裡照日期、時間先後排；取前 5 筆。

**專程候選**（該日在相關場館完全沒有既有課程可貼靠）：

- 學生時段涵蓋的日期中，如果當天相關場館沒有任何占用課程，列為專程候選。
- 只標記日期，不計算具體時段（沒有基準點可推算合理時間），由使用者自行決定時段，訊息中註明「需專程前往」。
- 如果教練當天在其他地區另有課程，附註已占用的時段（例如「當天 14:00-16:00 已在森域有課」），方便教練判斷。這段附註只會出現在 API 回應裡，不會放進給學生的訊息。

## 輸出格式範例

```
貼靠候選（交通最省）：
・9/16(二) 19:00-20:00，動智羽球館（緊接既有課程）

專程候選（該日目前沒有其他排課）：
・9/17(三) 全天可談，需自行決定時段
```

- 沒有任何候選時，輸出「這段時間目前排不進去，要不要換個日期？」
- 跨館貼靠的括號說明改成「（同日在此館另有課程）」，不透露其他學生的資訊。

## API

- `GET / PUT /api/venue-travel-times`：查看與整批設定車程表。
- `POST /api/booking-requests/{id}/suggest`：對一筆已解析的約課紀錄產生候選。
  - 請求（全部選填，用來覆蓋解析結果）：`duration_minutes`、`venue_ids`
  - 回應：`anchored_candidates`（日期、開始、結束、場館、是否跨館、錨點課程 id）、`dedicated_dates`（日期、當天其他占用時段）、`message`（範本組好的文字）
  - `resolved_windows` 為空（例如 `intent = other`，或解析失敗）時，回 422 並附上清楚的原因。

## 頁面

新增一個簡單頁面「找空檔」（原生 HTML/JS，沿用現有頁面的樣式）：

1. 貼上學生訊息 → 呼叫 parse → 顯示解析結果（學生、地區、時段、時長），並標出需要人工確認的地方。
2. 可以手動改時長、勾選場館 → 呼叫 suggest。
3. 顯示候選清單，以及組好的訊息，附一個「複製」按鈕。
4. 車程表維護：同一頁放一個可編輯的表格（6 個場館兩兩一組）。

## 不在本階段範圍

- 選定候選後自動建立課程（下一階段）。
- 查詢場館實際有沒有空場（這裡只看教練自己的行事曆）。
- `reschedule` / `cancel` 意圖的處理。

## 完成條件

- pytest 涵蓋：同館前後貼靠、跨館車程推算、跨館不足 120 分鐘被剔除、別館課程造成的衝突、趕不上下一堂別館課被剔除、工作時段邊界、學生時段過濾、請假時段釋放、去重、專程候選判定、查不到車程的組合。
- 用真實行事曆資料，對 3 則以上的真實訊息跑一次，由教練確認候選合理。
