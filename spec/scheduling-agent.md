# 找空檔（Phase 2）

## 目的

學生提出時間需求（例如「9/30 到 10/4 在台北」），教練自己選好日期範圍、時段、地區、時長，系統比對既有行事曆，找出最省交通時間的候選時段，產生一段可直接複製給學生的訊息。

## 整體流程

```
教練選條件（日期範圍 + 時段 + 場館 + 時長）
        → [找空檔，純程式] → 候選時段
        → [固定範本組字] → 可複製給學生的訊息
```

- 整個流程不呼叫 LLM：不花 token、結果可預期、好測試。
- 原本的設計是先用 Phase 1 的 LLM 解析學生訊息，再自動找空檔。實際用真實訊息試跑後改掉（2026-09-29）：同一句話 LLM 有時判成約課、有時判成閒聊，而且學生的訊息本來就常常要教練自己判斷，讓教練直接選條件比較實用。
- Phase 1 的解析功能（`POST /api/booking-requests/parse`）程式與測試保留，只是這個頁面不再呼叫。

## 新增資料表

```
venue_travel_times (id,
                     venue_a_id FK, venue_b_id FK,
                     travel_minutes)
```

場館兩兩之間的固定車程對照表，同場館車程視為 0，不用建表查詢。

- 雙向共用一筆：存的時候固定 `venue_a_id < venue_b_id`，查詢時兩個方向都查得到。
- 查不到車程的場館組合一律視為「不可銜接」（不要猜一個預設值），跨館候選直接剔除。
- 車程數字不由程式推估。目前的數字（2026-09-29）是用 Google Maps 查開車時間（週二上午路況、推薦路線、單一方向），教練要求每組再加 20% 緩衝（無條件進位）；之後由教練在頁面上自行調整。

## 架構原則

找空檔的運算邏輯用一般程式處理，不交給 LLM 推理，確保結果可預期、不會算錯。

## 參數與預設值

| 項目 | 規則 |
|---|---|
| 工作時段 | 08:00–22:30。候選不得早於 08:00 開始，也不得晚於 22:30 結束（常數，之後要改只改一個地方） |
| 占用時段的課程 | `status` 為 `scheduled` / `completed`。`cancelled` 與 `leave`（請假）都視為時段已釋放 |
| 日期範圍 | 教練選開始與結束日期，一次最多 31 天 |
| 候選時長 | 教練選，預設 60 分鐘（30–240） |
| 相關場館 | 教練勾選，至少一個。頁面提供「台北場館」「新竹場館」快選，依 `venue_areas` 表的「台北」「新竹」對照 |
| 學生時段 | 教練選每天的時段（全天／早上／下午／晚上／自訂），套用到範圍內每一天。候選的**開始時間**必須落在時段內；不要求整堂都在裡面（例如「晚上 18:00-22:00」時，21:30 開始、22:30 下課的課也算），結束時間由工作時段把關 |
| 貼靠候選上限 | 最多列 5 筆 |

## 候選時段演算法

**貼靠候選**（緊貼既有課程，交通最省）：

1. 撈出學生時段涵蓋日期內的所有占用課程（**所有場館**，因為教練人只有一個，別館的課也會卡住時間）。
2. 對每一筆既有課程（錨點），對每一個相關場館 V，往外長出最多兩個候選時段：
   - 之後：開始時間 = 錨點結束 + 車程(錨點場館 → V)
   - 之前：結束時間 = 錨點開始 − 車程(V → 錨點場館)
   - 同場館車程為 0，就是緊貼。
3. 基本過濾：
   - 超出工作時段 → 剔除
   - 開始時間不在學生時段內 → 剔除
   - 不在相關場館 → 剔除
4. 排除衝突：候選時段前後各加上車程後，跟任何一筆占用課程重疊 → 剔除。也就是說，候選前一堂在別館的話，要來得及趕過來；候選後一堂在別館的話，要來得及趕過去。
5. 跨館門檻：候選跟錨點不同館時，計算候選所在場館當天的連續時數（候選本身，加上同館中跟它首尾相接、間隔 0 分鐘的既有課程），須 ≥ 120 分鐘才通過，否則剔除（去程回程換不到兩小時不划算）。
   - 跟原版的差異：原版把「其他候選」也算進連續時數，但候選之間是互斥的選項，學生最後只會選一個，所以不能加總，這裡只算既有課程。
6. 去重：不同錨點生出的候選，如果日期、時段、場館完全相同，只保留一筆。
7. 排序：同館貼靠優先，再來是跨館貼靠；同一類裡照日期、時間先後排；取前 5 筆。

**彈性日**（原「專程候選」：當天沒有貼靠候選，但有真的趕得到的空檔）：

- 對範圍內的每一天：當天沒有任何貼靠候選（用取前 5 筆之前的完整清單判斷），就以半小時為單位掃描開始時間。某個開始時間可行的條件：晚於現在、落在學生時段內、整堂在工作時段內，而且至少有一個相關場館「趕得到」——跟貼靠候選用同一套判斷，從前一堂課的場館開過來來得及、下課後趕去下一堂課來得及，查不到車程一樣視為趕不到。
- 可行的開始時間合併成連續時段，例如「20:30-22:30」代表 20:30 到 21:30 之間開始都可以；有可行時段才列出這一天。
- 為什麼要算車程：真實案例 10/4 白天在新竹上課到 19:00，查台北場館時，不算車程會把 14:00-16:00 的空檔也當成可以約，但新竹台北單程就要 77 分鐘，實際上只有 20:30 以後去得了。
- 當天已占用的時段（不限場館）附在 API 回應裡給教練參考，不會放進給學生的訊息。

## 輸出格式範例

訊息是直接給學生看的，不出現「貼靠」「專程」「既有課程」這類內部用語，也不寫是接在哪堂課前後（不透露其他學生的資訊）：

```
我這幾個時段可以：
・9/30(三) 09:00-10:00 快羽會館
・9/30(三) 15:30-16:30 森域羽球運動會館

這幾天比較彈性，時間可以再討論：
・10/3(六) 08:00-22:30
・10/4(日) 20:30-22:30
```

- 沒有任何候選時，輸出「這段時間目前排不進去，要不要換個日期？」

## API

- `GET / PUT /api/venue-travel-times`：查看與整批設定車程表。
- `GET /api/slot-search/areas`：回傳 `{"台北": [場館 id], "新竹": [場館 id]}`，給頁面快選按鈕用。
- `POST /api/slot-search`：
  - 請求：`date_from`、`date_to`、`time_from`（預設 08:00）、`time_to`（預設 22:30）、`venue_ids`（至少一個）、`duration_minutes`（預設 60）
  - 回應：`anchored_candidates`（日期、開始、結束、場館、是否跨館、錨點課程 id）、`dedicated_dates`（日期、可行時段、當天其他占用時段）、`message`（範本組好的文字）
  - 日期或時間範圍不合理、超過 31 天、場館不存在時回 422。

## 頁面

「找空檔」頁面（原生 HTML/JS，沿用現有頁面的樣式）：

1. 選條件：日期範圍、時段（全天／早上／下午／晚上／自訂）、場館（「台北場館」「新竹場館」快選，可再手動勾選）、時長。
2. 按「找空檔」→ 顯示候選表格（教練看：類型、當天其他占用時段）與組好的訊息，附「複製」按鈕，訊息可以手動修改。
3. 車程表維護：同一頁可摺疊的表格（場館兩兩一組）。

## 不在本階段範圍

- 選定候選後自動建立課程（下一階段）。
- 查詢場館實際有沒有空場（這裡只看教練自己的行事曆）。

## 完成條件

- pytest 涵蓋：同館前後貼靠、跨館車程推算、跨館不足 120 分鐘被剔除、別館課程造成的衝突、趕不上下一堂別館課被剔除、工作時段邊界、學生時段過濾、請假時段釋放、去重、彈性日判定（含車程、已過去的時間）、查不到車程的組合。
- 用真實行事曆資料，對 3 組以上真實的學生需求跑一次，由教練確認候選合理。
