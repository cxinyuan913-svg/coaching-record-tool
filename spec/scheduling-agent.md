# 找空檔（Phase 2）

## 目的

學生提出時間需求（例如「9/30 到 10/4 在台北」），教練自己選好日期範圍、時段、地區、時長，系統比對既有行事曆，找出最省交通時間的候選時段，產生一段可直接複製給學生的訊息。

## 整體流程

```
教練選條件（日期範圍 + 時段 + 場館 + 時長）
        → [找空檔，純程式] → 候選時段
        → [固定範本組字] → 可複製給學生的訊息
```

- 整個流程不呼叫 LLM：不花 token、結果可預期、好測試。
- 原本的設計是先用 Phase 1 的 LLM 解析學生訊息，再自動找空檔。實際用真實訊息試跑後改掉（2026-09-29）：同一句話 LLM 有時判成約課、有時判成閒聊，而且學生的訊息本來就常常要教練自己判斷，讓教練直接選條件比較實用。
- Phase 1 的解析功能（`POST /api/booking-requests/parse`）程式與測試保留，只是這個頁面不再呼叫。

## 新增資料表

```
venue_travel_times (id,
                     venue_a_id FK, venue_b_id FK,
                     travel_minutes)
```

場館兩兩之間的固定車程對照表，同場館車程視為 0，不用建表查詢。

- 雙向共用一筆：存的時候固定 `venue_a_id < venue_b_id`，查詢時兩個方向都查得到。
- 查不到車程的場館組合一律視為「趕不到」（不要猜一個預設值）。
- 車程數字不由程式推估。目前的數字（2026-09-29）是用 Google Maps 查開車時間（週二上午路況、推薦路線、單一方向），教練要求每組再加 20% 緩衝（無條件進位）；之後由教練在頁面上自行調整。

## 架構原則

找空檔的運算邏輯用一般程式處理，不交給 LLM 推理，確保結果可預期、不會算錯。

## 參數與預設值

| 項目 | 規則 |
|---|---|
| 工作時段 | 08:00–22:30。候選不得早於 08:00 開始，也不得晚於 22:30 結束（常數，之後要改只改一個地方） |
| 占用時段的課程 | `status` 為 `scheduled` / `completed`。`cancelled` 與 `leave`（請假）都視為時段已釋放 |
| 日期範圍 | 教練選開始與結束日期，一次最多 31 天 |
| 候選時長 | 教練選，預設 60 分鐘（30–240） |
| 相關場館 | 教練勾選，至少一個。頁面提供「台北場館」「新竹場館」快選，依 `venue_areas` 表的「台北」「新竹」對照 |
| 學生時段 | 教練選每天的時段（全天／早上／下午／晚上／自訂），套用到範圍內每一天。候選的**開始時間**必須落在時段內；不要求整堂都在裡面（例如「晚上 18:00-22:00」時，21:30 開始、22:30 下課的課也算），結束時間由工作時段把關 |
| 同館接課上限 | 最多列 5 筆 |
| 大空檔最短長度 | 2 小時（從最早開始到最晚下課） |
| 大空檔開始時間 | 只用整點（08:00、09:00…），教練要求訊息好讀 |

## 候選時段演算法

結果分兩組（2026-09-29 教練要求）：第一組是交通最省的具體時段，第二組是讓學生自己挑的大段空檔，可以包含多個場館、多個時段。

共用的「趕得到」判斷：候選時段不跟任何占用課程重疊（**所有場館**的課都算，教練人只有一個），而且從前一堂課的場館開過來來得及、下課後趕去下一堂課來得及；查不到車程的組合視為趕不到。另外要晚於現在、開始時間落在學生時段內、整堂在工作時段內。

**第一組：同館接課**（緊接既有課程、同一個場館，交通最省）：

1. 對相關場館的每一堂既有課程，長出兩個候選：接在後面（開始 = 該堂結束）、接在前面（結束 = 該堂開始）。
2. 用「趕得到」判斷過濾（例如接在後面的候選，下一堂如果在別館，要來得及趕過去）。
3. 去重：同一個時段被前後兩堂課同時長出來時只留一筆。
4. 照時間先後排序，取前 5 筆。
- 不列換館接課（例如上完快羽的課開車去森域接下一堂）：教練決定第一組只列同館，換館的情況會出現在第二組的大空檔裡，不會漏掉。

**第二組：大空檔**（至少 2 小時，已算車程）：

1. 對範圍內的每一天、每一個相關場館，以**整點**為單位掃描開始時間，用「趕得到」判斷；連續可行的開始時間合併成一段（最早開始 ～ 最晚下課）。因為只用整點，一小時的課最晚 21:00 開始，大空檔最晚到 22:00。
2. 長度不到 2 小時的剔除（零碎空檔不列）。
3. 同一天不同場館的時段差不多時合併成一筆：場館取聯集，時段取大家都可以的共同範圍。例如三蘆 16:00-22:00、快羽/森域/海龍王 17:00-22:00 → 「17:00-22:00 快羽、森域、三蘆、海龍王」，三蘆多出來的那一小時不另外列（教練要求，訊息短比較重要）。
   - 「差不多」的定義：開始、結束時間都相差 ≤ 1 小時，而且共同範圍仍至少 2 小時。相差更多就分開列，避免例如 08:00-12:00 跟 10:00-12:00 合併後前者少掉一半。
4. 每天都列，不管當天有沒有同館接課（兩組是不同用途，可以重疊）。
- 為什麼要算車程：真實案例 10/4 白天在新竹上課到 19:00，查台北場館時，不算車程會把 14:00-16:00 的空檔也當成可以約，但新竹台北單程就要 77 分鐘，最早 21:00 才到得了，只剩 1 小時，不列為大空檔。
- 當天已占用的時段（不限場館）附在 API 回應裡給教練參考，不會放進給學生的訊息。

## 輸出格式範例

訊息是直接給學生看的，不出現「接課」「空檔」「既有課程」這類內部用語，也不寫是接在哪堂課前後（不透露其他學生的資訊）：

```
我這幾個時段最方便：
・9/30(三) 09:00-10:00 快羽會館
・10/1(四) 10:00-11:00 快羽會館

其他有空的時段（場館可以選）：
・9/30(三) 17:00-22:00 快羽會館、森域羽球運動會館、三蘆羽球館、海龍王 羽球學苑（羽球館
・10/3(六) 12:00-22:00 快羽會館、森域羽球運動會館、三蘆羽球館、海龍王 羽球學苑（羽球館
```

- 沒有任何候選時，輸出「這段時間目前排不進去，要不要換個日期？」

## API

- `GET / PUT /api/venue-travel-times`：查看與整批設定車程表。
- `GET /api/slot-search/areas`：回傳 `{"台北": [場館 id], "新竹": [場館 id]}`，給頁面快選按鈕用。
- `POST /api/slot-search`：
  - 請求：`date_from`、`date_to`、`time_from`（預設 08:00）、`time_to`（預設 22:30）、`venue_ids`（至少一個）、`duration_minutes`（預設 60）
  - 回應：`anchored_candidates`（第一組：日期、開始、結束、場館、錨點課程 id）、`open_blocks`（第二組：日期、開始、結束、場館清單、當天其他占用時段）、`message`（範本組好的文字）
  - 日期或時間範圍不合理、超過 31 天、場館不存在時回 422。

## 頁面

「找空檔」頁面（原生 HTML/JS，沿用現有頁面的樣式）：

1. 選條件：日期範圍、時段（全天／早上／下午／晚上／自訂）、場館（「台北場館」「新竹場館」快選，可再手動勾選）、時長。
2. 按「找空檔」→ 顯示分兩組的候選表格（教練看：大空檔共幾小時、當天其他占用時段）與組好的訊息，附「複製」按鈕，訊息可以手動修改。
3. 車程表維護：同一頁可摺疊的表格（場館兩兩一組）。

## 固定時段排課（每週同一天，連續 N 週）

2026-10-03 新增。情境：新學生每週六都可以，要排連續 8 週、每次一小時；其他學生的週六課每週都不一樣，一週一週比對很難找到最適合的固定時段。「找空檔」頁面新增「固定時段（多週）」分頁。

- **輸入**：星期幾、起始日期（從這天起第一個符合的星期開始）、連續幾週（1–20，預設 8）、每天時段、場館、時長。
- **候選**：每個「相關場館 × 整點開始時間」（教練要求只用整點），開始時間落在時段內、整堂在工作時段內。
- **逐週檢查**：用跟找空檔同一套「趕得到」判斷（不撞課、前後趕得到、算車程、查不到車程視為趕不到、晚於現在）。
- **順延**：某週不行就跳過、往後補一週，最多順延 2 週（跟套組請假順延的概念一致）；湊不滿 N 堂的候選不列。
- **排序**：順延週數少的優先 → 同館接課（緊接同館既有課程前後）週數多的優先 → 當天本來就在這個館的週數多的優先 → 時間早的優先；列前 10 名。
- **輸出**：每個方案的實際上課日期、被跳過的週與原因（只給教練看，例如「撞到 09:00-10:00 動智的課」「前一堂 12:00 在動智下課，趕不過來」）。
- **給學生的訊息**（2026-10-03 教練要求跟課程套組頁「課程訊息」同一個格式，前端組字、共用 common.js 的 chineseNumber；學生還沒付款，不放付費日期與匯款資訊；只在同一個館，所以地點寫一行就好）：

```
地點：快羽會館
第一堂課：10/10（六）10:00～11:00
第二堂課：10/17（六）09:00～10:00
…
```

- **API**：`POST /api/slot-search/recurring`，請求 `weekday`（週一=0 … 週日=6）、`date_from`、`weeks`、`time_from`、`time_to`、`venue_ids`、`duration_minutes`；回應 `first_date`、`weeks`、`options[]`（場館、開始結束時間、`dates`、`skipped[]`、`adjacent_weeks`、`same_venue_weeks`）。

### 指定希望時段：逐週排排看

教練常常已經有心目中的時段（例如每週六 10:00、快羽），要的是「照這個排排看，哪幾週有問題、怎麼調最方便」。表單填了「希望開始時間」就進入這個模式（只能勾一個場館，教練決定只在同一個館換時段、不換館）。逐週三種狀況：

| 狀況 | 系統怎麼做 |
|---|---|
| 指定時段可以，而且剛好接在同館課程前後 | 直接排定 |
| 指定時段可以，但前後 2 小時內有同館課程可以接（例：8–9 有課，10–11 空著） | 💡 提示「改 9:00～10:00，接在 08:00-09:00 那堂後面，比較方便」，教練一鍵改或維持 |
| 撞課或趕不到 | ⚠ 列出當天同館其他可行時段最多 4 個：同館接課的優先（跟著既有課程時間走，13:30 下課就從 13:30 開始），其次是整點空檔，同類依離指定時間近的優先；預設先選最方便的那個，也可以選「這週跳過，往後順延一週」 |

- 每週的選擇在前端即時改，學生訊息跟著更新；跳過幾週就往後順延幾週，最多順延 2 週，排不滿時顯示還差幾堂。
- **API**：`POST /api/slot-search/recurring/plan`，請求 `weekday`、`date_from`、`weeks`、`preferred_start`、`venue_id`、`time_from`／`time_to`（替代時段範圍）、`duration_minutes`；回應 `week_plans[]`（共 weeks+2 週：`preferred_ok`、`preferred_adjacent`、`preferred_reason`、`suggestion`、`alternatives[]`、`day_busy[]`）。
- **一鍵建立課程套組**（2026-10-03 加入）：推薦方案卡片與逐週排排看都有「建立課程套組」按鈕，跳出小視窗。日期、每堂時間、場館、時長直接帶入（不能在視窗裡改）；教練補學生（可在視窗裡直接新增學生：姓名＋身份別）、套組名稱（預設「週六固定 8 堂」）、教練費與場地費／小時、購買日期（今天）、收款狀態（未收款）。
  - `POST /api/packages` 新增選填欄位 `sessions: [{date, start_time}]`（每堂各自時間，逐週排排看某幾週改成接課時間時用；有給就忽略 `session_dates`）與 `check_conflicts`（一鍵建立時為 true：建立前逐堂檢查跟既有排定／已完成課程（不限場館）有沒有時間重疊，有就整筆不建立、回 409 並列出哪幾堂）。課程套組頁原本的建立方式不帶這兩個欄位，行為不變。
  - 套組的 `recur_start_time` 用出現最多次的開始時間。
  - 正式給學生的訊息（含付費日期與匯款資訊）仍從課程套組頁的「課程訊息」產生。

## 不在本階段範圍

- 選定候選後自動建立課程（下一階段）。
- 查詢場館實際有沒有空場（這裡只看教練自己的行事曆）。

## 完成條件

- pytest 涵蓋：同館前後接課、別館課程造成的衝突、趕不上下一堂別館課被剔除、工作時段邊界、學生時段過濾、請假時段釋放、去重、不列換館接課、大空檔（含車程、整點、2 小時門檻、場館合併規則、已過去的時間）、查不到車程的組合。
- 用真實行事曆資料，對 3 組以上真實的學生需求跑一次，由教練確認候選合理。
